# Запуски ДЗ5

## Утверждённая постановка

| Конфигурация | Reward | KL beta |
|---|---|---:|
| A_strict | Полное совпадение мультимножества вызовов и аргументов | 0.02 |
| B_partial | Оптимальное сопоставление вызовов, F1 аргументов | 0.02 |
| C_partial_kl | Та же partial | 0.10 |

Для одинаковых имён `s=.25+.75*(2*C/(Ap+Ag))`; C - совпавшие пары ключ-значение, Ap/Ag - количества аргументов. Для двух пустых наборов F1=1, для разных имён s=0. Сопоставление один к одному максимизирует sum(s), итог `2*sum(s)/(Np+Ng)`. Сохраняются повторы и штраф за лишние/пропущенные вызовы. Вложенное значение сравнивается целиком. Порядок ключей/вызовов не влияет. 1 и 1.0 равны, bool и строки отличаются от чисел. Default не подставляется.

Для эталона no-call непустой ответ без вызовов даёт 1. Пустой, обрезанный или сломанный ответ даёт 0 во всех вариантах. EOS сам по себе считается пустым ответом. Перед штатным `Qwen3CoderToolParser` проверяется целостность всей XML-разметки; дубликаты параметров и частично восстановленные вызовы отклоняются. Схемы переменные, передаются в парсер отдельно для каждого prompt. Никаких внешних функций инструменты реально не исполняют.

## Общие настройки

GRPO, LoRA r=16 / alpha=32 на linear-слоях языковой части, без изменения vision и tokenizer. BF16, seed/data_seed 42, LR 1e-5, AdamW, constant LR, 32 optimizer steps, batch 1, accumulation 8, 4 генерации на prompt (2 исходных prompts на шаг). Это короткий бюджет: около 64 prompts из перемешанного train на конфигурацию. Сохранение и validation на шагах 16 и 32; лучший чекпойнт выбирается по одной и той же common strict метрике на фиксированных 64 примерах validation, выбранных хешированием ID. Итоговая ToolACE validation - все 1165 примеров с temperature=0.

Training/data seed - 42; у colocated vLLM в TRL 1.16.0 rollout seed равен 0 во всех трёх запусках (штатная инициализация движка). Evaluation seed - 42. Rollout: temperature=1, top_p=1, max_completion_length=1024, thinking off, контекст до 4096. Слишком длинные/обрезанные rollout-ответы имеют reward 0 и исключены из policy loss. Для KL используется исходная политика через отключение PEFT-адаптера. Все запуски начинают с одной исходной ревизии, без SFT. BFCL применяется после выбора чекпойнта; его результаты не меняют обучение. GRPO smoke фиксируется после первого конечного loss/reward/gradient и optimizer step, в `training/grpo_smoke.json`.

## Команды внутри образа задания

Из корня репозитория, с подготовленным `eda_outputs`:

```bash
python3 -m unittest discover -s hw5_rl -p test_rewards.py -v
python3 hw5_rl/native_smoke.py
python3 hw5_rl/run_pipeline.py --runs /workspace/hw5_rl/runs/run_02
```

Pipeline последовательно выполняет baseline BFCL и ToolACE validation, затем train/merge/full validation/BFCL для A/B/C. Каждый GPU-процесс завершён до следующего, используются `CUDA_VISIBLE_DEVICES=0` и Docker `--gpus device=0`. `materials/evaluate.py` запускается с cwd `materials`, файлы evaluator/benchmark сверяются с SHA256 из provenance. Полные веса создаются `merge.py`; evaluator всегда загружает исходный tokenizer нужной ревизии. `--resume` пропускает только уже завершённые стадии, но не перезаписывает незавершённое обучение.

Для графиков на ноутбуке:

```bash
pip install -r hw5_rl/requirements-plot.txt
python3 hw5_rl/summarize.py --runs hw5_rl/runs/run_02
python3 hw5_rl/analyze_errors.py --runs hw5_rl/runs/run_02
```

`build_report.py` формирует PDF из реально сохранённых результатов. Для него нужны reportlab и Arial с кириллицей; на ноутбуке использован bundled Python Codex. Потери GRPO и reward отражены отдельно, определения strict/partial различаются. Автоматический разбор ошибок выбирает первые два ID каждого исхода: исправление, регрессия, оставшаяся ошибка.

## Расположение и статус

Использована одна NVIDIA A100-SXM4-80GB учебного сервера; другая карта не занималась. Docker image ID `sha256:36834baae53d14832cef3c626c2714d4b972a738d519c50bb3e643b9633ef011`. Адреса и инструкции доступа к приватным весам сохранены локально в LOCAL_ARTIFACTS.md и не включаются в публичный Git.

Точный журнал стадий - `runs/run_02/run_status.json`. Успешный статус обучения подтверждается `training_metrics.json` и выбранным adapter; оценка - `bfcl/metrics.json` и ровно 350 строками `bfcl/predictions.jsonl`. Плановые параметры не подтверждают выполнения запуска. Незавершённые стадии не получают вымышленных metrics или predictions.

Объёмные исходные данные и train/validation восстанавливаются `eda.py`; сохраняются их SHA256 и split manifest. Полные merged веса и промежуточные checkpoint лежат на сервере; адаптеры, configs, логи, оценки, графики и PDF копируются в локальный каталог работы. Ничего не опубликовано и не отправлено в Stepik.

Диагностический run_01 планировался на 128 шагов и намеренно прерван после 10 optimizer steps из-за времени. Он исключён из сравнения A/B/C. Его неизменённый baseline и пройденная проверка native parser повторно использованы в run_02; происхождение отмечено в журнале стадий.

Полная CPU-проверка audit_targets.py подтвердила round trip всех 9603 эталонов с вызовами через реальный Qwen template и vLLM parser, без изменения данных; reference_audit.json содержит счётчики и пустой список исключений.
